# 0.2.0 design brief: streaming deflate and gzip header control

**Status: needs design.** This document is the problem statement, the
constraints, and the acceptance criteria. It deliberately does not prescribe the
API — that is the job of whoever designs this.

Read [../internals.md](../internals.md) first: the memory model, the pinned
layouts, and the FFI review gates all apply unchanged.

---

## 1. What the library is, and where it stands

`goose-igzip` binds **igzip** — ISA-L's gzip implementation — to Goose. It is a
Goose package: `igzip.goose` is the entry, `igzip.build` names the CMake target
`igzip_goose`, and `src/igzip_shim.c` is the C adapter. ISA-L 2.32.1 is a pinned
submodule built from source; nothing is installed system-wide.

```bash
make check        # typecheck the package
make test         # Goose tests, then inflate every stream they wrote
make verify       # check + tests + thread test + examples
make stress       # AddressSanitizer check of the output bound
make bench        # the trained-table benchmark
```

0.1.0 ships the **stateless** half:

| | |
|---|---|
| `igzip::Compressor` | 299,472 B (an 82,384-byte `isal_zstream` + a 217,088-byte level buffer), created by `compressor(wrap, level)` / `gzip_compressor(level)` / … |
| `compress(c, src, out)` / `compressed(c, src)` | one whole body in, one gzip/zlib/raw member out; appends to a builder or returns a fresh one |
| `Trainer`, `Histogram`, `HuffTables` | 18,912 / 2,528 / 2,232 B; `add`, `symbols`, `build`, `counts`, `trainer_of` |
| `set_tables` / `clear_tables` | attach a trained table, which pins the level to 0 |
| `Status` + `ok` / `status_name` | the only failure channel; nothing aborts on bad input |

The whole body must be in memory before the call, and the output goes straight
into the destination builder with `bound(n)` as the limit. That is fast — a
trained table reaches ~3.8x level 1's throughput at 104% of its bytes on
1.9 KB responses — but it is one shot.

## 2. The problem: four capabilities, one state machine

Every item below needs the **stateful** `isal_deflate` path rather than
`isal_deflate_stateless`. That is what makes this a single design problem rather
than four small features.

1. **Compress as the body is produced.** A gzip middleware wrapping a handler
   does not have the whole response: it has chunks, and it must emit bytes as
   they arrive. Today the only option is to buffer the entire body, compress it
   stateless, and then hand it over — which is exactly what the middleware
   exists to avoid for large or streamed responses (proxied upstreams, SSE,
   generated reports).
2. **Control the gzip header.** 0.1.0 emits igzip's generic header: mtime 0 (good
   — reproducible), OS byte 0xff, no name or comment. A caller needs to set the
   OS byte, optionally a name/comment/extra field, and for zlib set the window
   size and level hint. Without this, two servers with different settings produce
   different bytes for the same content, and a cache keyed on the compressed
   bytes cannot be shared.
3. **Inputs above 2 GiB.** `MAX_INPUT` is 0x7FFFFFF0 because `avail_in` is
   `uint32_t`. A streaming API feeds igzip one 32-bit length at a time, so the
   limit disappears — but only if the design feeds it in chunks.
4. **A preset dictionary** (`isal_deflate_set_dict`) for bodies that share a
   prefix, such as a JSON envelope or an HTML shell.

The natural consumer is the same one the training API serves: a per-thread
compressor, held across requests, that can also be handed a body in pieces. Note
that a caller may hold **both** a `Compressor` and whatever this design adds:
budget the new value's size accordingly (a 64 KiB internal chunk buffer on top
of 300 KB is acceptable; a second 300 KB per thread may not be).

## 3. Hard constraints

- **C owns no memory.** No `malloc`, no handle to close. State lives in the
  Goose value and the owning scope is the free.
- **No API break.** Every 0.1.0 signature keeps working and producing the same
  bytes.
- **Layouts pinned.** Any new mirrored C struct needs `_Static_assert`s for size
  and every offset the shim indexes.
- **Build shape unchanged.** Native code is the CMake target `igzip_goose`; no
  `c_libs`, no `extern "igzip"` block, no system install.
- **Goose has no named arguments, no tuples, no `?`, and no truthiness.** A call
  site has to read well positionally, and a `Status` needs `.ok()`.

## 4. ISA-L facts you can rely on

From the vendored headers (`vendor/isa-l/include/igzip_lib.h`) and from
measurements recorded in [../../ROADMAP.md](../../ROADMAP.md):

| Fact | Consequence for the design |
|---|---|
| `void isal_deflate_init(struct isal_zstream *)` then `int isal_deflate(struct isal_zstream *)`, called repeatedly | the state machine is per-value and progresses across calls |
| `isal_deflate_reset(stream)` | a finished or aborted stream can be reused without rebuilding the value |
| `NO_FLUSH` (0), `SYNC_FLUSH` (1), `FULL_FLUSH` (2) in `stream->flush` | `SYNC`/`FULL` byte-align by appending an empty stored block, so the bytes so far are a complete decode point; `FULL` also drops the LZ77 history so a following block is independent |
| `stream->end_of_stream = 1` marks the last call | a `finish` needs its own entry point, and a stream must not accept input afterwards until reset |
| `isal_deflate_set_hufftables` is legal "before compression start or after the successful completion of a SYNC_FLUSH or FULL_FLUSH" | a trained table cannot be swapped mid-block; the API must make the legal moments obvious or refuse the others |
| `isal_write_gzip_header(stream, &hdr)` with `gzip_flag = IGZIP_GZIP_NO_HDR` writes a custom header and only the trailer afterwards; `isal_gzip_header_init` seeds the defaults | header control is opt-in per stream, and the default path stays as it is |
| `struct isal_gzip_header` fields: `text, time, xflags, os, extra/extra_buf_len/extra_len, name/name_buf_len, comment/comment_buf_len, hcrc, flags` | the Goose value mirrors only what a caller should set; the buffer lengths are igzip writing into caller storage, which Goose must own |
| `struct isal_zlib_header` fields: `info` (window bits − 8), `level`, `dict_id`, `dict_flag` | zlib needs its own header value or a shared abstraction |
| Completion: after `end_of_stream` with `NO_FLUSH`, "checking that the out_buffer is not empty or that `internal_state.state = ZSTATE_NEW_HDR` is sufficient" | completion is observable, but through `internal_state` — decide whether to lean on that and say so in a comment |
| `avail_in`/`avail_out` are `uint32_t`; a chunked loop feeds arbitrary lengths | >2 GiB works if the shim loops in ≤ 2^32 chunks |
| **Streaming needs no output bound**: igzip writes into `next_out` up to `avail_out` and returns | unlike `compress`, there is no `bound(n)` and no overrun hazard, provided `avail_out` is honest every call |
| Measured: a chunked `isal_deflate` loop with a 64 KiB output buffer produced output **byte-identical** to the stateless path (120,233 bytes in, 8,045 out, `memcmp` equal) | a one-shot streaming write can be used as a cross-check, and the two paths cannot disagree about format |
| Measured: the naive shape — level buffer, chunk buffer and `isal_zstream` all as C locals — needs **430 KB of C stack** per call (`ISAL_DEF_LVL1_DEFAULT` alone is 282,624) | buffers belong in the Goose value; do not repeat this |
| `isal_deflate_set_dict(stream, dict, dict_len)` | the dictionary is borrowed for the stream's life: igzip copies it? — verify before designing, and record the answer |

## 5. Design questions

Answer these explicitly. Each has a recommended starting point, but none is
settled; disagree where you have a reason.

**Q1 — New value, or extend `Compressor`?** A `Deflater` type alongside
`Compressor` keeps the one-shot path untouched, but a thread that wants both now
holds ~600 KB. Extending `Compressor` saves nothing (the level buffer and stream
are already there) and keeps one type to learn, at the cost of a mode flag inside
it. Recommend: separate type, because the state machine and the failure modes
differ, and a single value would carry a "which mode am I in" flag that the type
system could have caught.

**Q2 — Where does output go?** Two shapes:
(a) the caller passes a builder and each call appends everything igzip produced,
with igzip writing into a bounded chunk buffer the value owns;
(b) the caller passes a builder as the destination and one call consumes as much
input as fits, returning how much it took, so no intermediate copy exists.
Recommend (a) for call-site simplicity unless the copy shows up in the bench:
Goose users do not want to loop over `avail_out`, and a 64 KiB chunk buffer is
cheap next to the 217,088-byte level buffer already in the value.

**Q3 — Flush and finish at the call site.** Options: one call with extra
arguments (`write(d, src, out, Flush.Sync, false)`), or separate verbs
(`write`, `flush`, `finish`). Goose has no named arguments, so two booleans in a
row would read badly. Recommend separate verbs plus an `enum Flush { None, Sync,
Full }` on the one call that takes it, if that stays under four parameters.

**Q4 — Header control: value or explicit write?** Either the deflater owns a
`Header` value set before the first write, or the caller writes the header itself
(`write_header(h, out)`) and the deflater runs with `GZIP_NO_HDR`. The second is
more flexible (the caller can write the header whenever it likes, and inspect the
bytes) and keeps the deflater simpler; the first is harder to misuse.
Recommend deciding by asking which the middleware needs — it needs the trailer
written automatically and the header written once, ahead of the first body byte.

**Q5 — Lifecycle.** What does `finish` do to the value, what does a second
`finish` do, what does `write` after `finish` do (Status value? refuse?), and
which one resets for the next body — `reset(d)`, or `finish` leaving it ready?
Recommend explicit `reset`, with every misuse a `Status`, because a silent reset
hides a bug in a server loop.

**Q6 — Copy semantics.** Goose copies fixed-size values silently, so a mid-stream
deflater can be copied into a second variable; both would then advance
independently and neither output would be correct. Decide: document "do not
copy", or make `write` take the value in a way that makes a copy visible, or add
a state value whose copy fails the `_Static_assert`… say what you choose and why.

**Q7 — `Status` additions.** Which new failure modes exist (wrong state, invalid
flush, header too large for the output?) and do they fit the existing `Status`
enum, or does it need new variants? Keep `status_name` accurate.

**Q8 — > 2 GiB.** Chunk the input inside C (a `while` over `uint32_t` windows) or
leave the limit and only lift it when a caller asks? If you chunk, say how it is
tested: a 5 GiB buffer is impractical in CI, so either a loop over a synthetic
repeat that reaches past 4 GiB in total input (allocating one 1 GiB arena and
feeding it five times is *not* the same stream — be careful), or a test-only
build flag that shrinks the window.

**Q9 — Trained tables mid-stream.** `set_hufftables` is legal only before the
first byte or after `SYNC`/`FULL`. Does `set_tables` on a deflater refuse while a
block is open, return a `Status`, or is it simply documented? Note that a
middleware switching a warmed table into a live stream is a real scenario.

**Q10 — Naming.** `Deflater`, `Writer`, `Stream`? gslib's Goose code (see the
readings below) spells its streaming API `gzip_writer(level)`, `gzip_write(w,
data, out)`, `gzip_flush(w, out)`, `gzip_close(w, out)`, and Goose's UFCS turns
those into `w.write(data, out)`. Familiarity is worth more than novelty here.

## 6. Acceptance criteria

The design is done when `make verify && make stress && make fmt-check` are green
**and** these hold:

1. **One-shot equivalence.** A stream written in a single `write` + `finish`
   produces bytes identical to `compressed(c, body)` for the same level and
   wrapper. (Measured to be true for a 120 KB body; make it a test.)
2. **Chunked equivalence.** The same body written in randomly sized chunks with
   no flush produced the same bytes as the one-shot stream, and inflates to the
   input with CPython's `zlib`/`gzip`.
3. **Flush points.** `Sync` and `Full` boundaries are decode points: a
   `zlib.decompressobj` fed only the prefix up to one flush returns all input so
   far; the rest decodes after. `Full` additionally makes the following block
   independent — assert with a repeated prefix that the bytes after the flush do
   not reference the history before it.
4. **Header control.** The written header carries the mtime, OS byte and name the
   caller asked for, verified by parsing the bytes (and by `gzip.decompress`
   round-tripping); with no header requested, the bytes match 0.1.0 exactly.
5. **Reproducibility.** Two runs over the same input produce identical bytes,
   including with a custom header (no clock leaks in).
6. **Dictionary.** Output decodes with `zlib.decompressobj(zdict=…)` and fails
   without it.
7. **Large input.** A strategy proven for inputs past `MAX_INPUT`, or a written
   argument for why the limit stays.
8. **Memory safety.** `make stress` extended: streaming writes into builders
   sized exactly, at flush points and at random chunk boundaries, under
   AddressSanitizer — igzip must never write past `avail_out`.
9. **Threads.** `test/threads.goose` still passes, and a streaming worker is
   added: one deflater per `thread_fn`, no globals.
10. **No 0.1.0 regressions.** The 25-stream suite and the bench numbers are
    unchanged.

## 7. What to hand back

1. An API sketch: types, signatures, and the state machine (`fresh → open →
   flushed → finished → reset`), with the call sites written out as a user would
   type them.
2. The C shim function list with exact signatures, and the `_Static_assert`s
   each mirrored struct needs.
3. A test plan mapped to the acceptance criteria, naming which files change.
4. Risks, and what you would cut first if it grows.
5. Then implement it behind the same gates: no new C memory, pinned layouts, FFI
   review gates respected.

## 8. Out of scope

Inflate (0.3.0), the checksums (0.4.0), erasure coding, RAID, memory kernels.
Do not change 0.1.0's API, do not introduce a heap handle, and do not move
`vendor/isa-l` off its pin.
